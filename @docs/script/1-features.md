# Part 1 — Features

Estimated delivery: 2–3 minutes at a conversational pace.

## Screen 1 — Start with the evidence

On screen: Open the Keystone dashboard and let the evidence window load.

Voiceover: “Now I’m switching to Keystone. This demo uses synthetic fixtures, so no real student or family data is involved. Before it shows a result, it shows whether evidence is ready. If the backend is starting or restoring, the page says so and retries automatically. No believable zeroes while the baseline is unavailable.”

## Screen 2 — See the trust posture

On screen: Show the evidence window, latest sync, source snapshots, trust posture, and key metrics.

Voiceover: “The overview tells me what I can trust: the evidence window, latest sync, source completeness, rule coverage, conflicts, pending review, and spend. The key boundary is visible: source writes are zero. A pending proposal is not a fix, and any auto-apply shown here is reversible state inside Keystone—not a source-system write.”

## Screen 3 — Find and filter the work

On screen: Open “Find the conflicts,” select “Active failures,” and briefly show the filters.

Voiceover: “Now I’ll open conflict evidence. These are versioned, repeatable checks—not predictions or edits. I can filter by issue type, source, status, proposal state, or confidence. If source data is unavailable, Keystone marks it Evidence gaps. Unchecked means ‘we could not verify this,’ not ‘everything is fine.’”

## Screen 4 — Inspect the reason

On screen: Open one conflict and scroll through invariant evidence, the proposal, lineage, and audit history.

Voiceover: “The detail view shows the rule, entities, disagreeing sources and fields, and expected verdict. I can compare raw and normalized values and the transformation between them. A proposal shows its action, target, evidence, cost, and confidence signals. Confidence is not a promise: incomplete or conflicting evidence lowers it. Sensitive fields receive a hard hold, and the audit history keeps the path visible.”

## Screen 5 — Decide deliberately

On screen: Show Approve, Reject, Hold, the reason field, and confirmation. Choose Hold for the walkthrough.

Voiceover: “A reviewer can approve, reject, or hold. Every decision requires a reason and confirmation. I’m choosing Hold because it demonstrates the safe path when more evidence is needed. The decision records reviewer intent and audit history in Keystone; it does not change the source mirror or any source system.”

## Screen 6 — Prioritize and add context

On screen: Briefly show “See the bigger pattern” and “Add support context.”

Voiceover: “Patterns group related failures so the team knows where to start. Support tickets connect issues to a student, household, source, owner, and requested action. Missing references stay marked as missing.”

## Close — The outcome

On screen: Return to the overview or leave “Synthetic fixtures · no source writer” visible.

Voiceover: “That’s the feature story: read-only evidence, explainable conflicts, and deliberate human decisions. Success is not automatic fixes. It’s a reviewer who understands the problem, chooses the safest next step, and keeps the trail intact.”
